Problem

Owner: Remi Colin · Status: draft for review · Companion docs: engineering spec and UX spec. Feasibility proven by the spike (spike record, real-device validated 2026-07-27, branch is reference-only).

Self verification lives on the phone. Every desktop verification forces a device switch: the user is on a website, gets a QR, must find their phone, unlock it, open Self, scan, approve, and return to the browser. On desktop, where most KYC/age-gated onboarding happens, that context switch is the biggest drop-off point in the funnel, and it repeats on every single verification. Password-manager-style browser extensions have taught users that identity actions can be two clicks in the corner of the screen.

Product

A Chrome extension that holds the user's Self account (transferred once from the phone, end-to-end encrypted) and approves disclosure requests directly in the browser. Proofs are generated in the same TEE pipeline as mobile: nothing in the proving chain changes, only where the approval happens.

One-line pitch. Link your phone once, then prove who you are from the browser in two clicks.

Enterprise verification flow · the extension is a new branch on the hosted page, everything upstream and downstream is unchanged

Users

  1. End users on desktop · verify without reaching for the phone. The phone remains the source of truth (registration, backup, recovery); the extension is a satellite.
  2. Enterprise relying parties · get higher desktop conversion for free. Zero integration: the Self-hosted verification page detects the extension and offers it instead of the QR. RPs keep calling sessions.create() exactly as documented.
  3. Self engineering · must not inherit a second product to maintain. The extension is a thin shell (~1.5k LOC) over the webview-app build, the SDK, the bridge contract, and Euclid; releases are fully automated to the Chrome Web Store.

What ships: functional requirements

#CapabilityRequirement
F1 Account link QR handshake phone to extension; E2E-encrypted transfer (P-256 ECDH + AES-256-GCM); emoji safety check gates the send: both devices show the same 4 emojis derived from the shared secret, and the user explicitly presses "Encrypt & send my account" on the phone after comparing
F2 Custody Passkey-first (Touch ID via WebAuthn PRF; no password exists in that mode); password fallback for non-PRF machines; lost-credential path = reset this browser + relink (phone unaffected)
F3 Disclosure Enterprise hosted verification page detects the extension, then popup with consent screen (requesting origin shown), then hold-to-approve, then TEE proof, then the same webhook the RP already handles; QR fallback whenever the extension is absent, locked, or stale
F4 Documents All document categories transfer (passport, EU ID, Aadhaar, KYC); user selects the active proving document in the extension
F5 Feedback Every wait has a state (per the UX spec loading inventory); failures are explicit and mirrored on both devices during linking
F6 Post-link lifecycle Re-link is the sync mechanism (linking again overwrites the browser copy). The extension detects a stale account at proof time via an account key epoch and fails closed to the QR path rather than proving from a superseded identity. Expired documents are marked in the popup and refused for proving. Linking requires at least one registered document.
F7 Custody lifetime Secrets and documents are always ciphertext at rest; the unlocked session ends on 30 min idle, 12h absolute, manual lock, OS session lock, or browser exit, and a lock mid-use fails closed (see the engineering spec session and lock policy)

Post-link lifecycle: the account is not frozen at link time

Transfer is a copy, so the browser and the phone can drift. Decisions:

EventBehavior in v1
New document registered on the phoneNot pushed. The user re-links to sync (the link flow overwrites the browser copy). The popup shows what it holds and when it was linked, so drift is visible rather than silent.
Document expiresMarked expired in the document list and refused for proving, with copy pointing at the phone.
Account recovered or rotated on the phoneSecurity-relevant, not polish: the browser copy must stop proving. The account carries a key epoch; the extension includes it at proof time and a mismatch fails closed to the QR path with a re-link prompt. Detection design lands in CEP-05.
Phone lost or stolenThe browser copy keeps working: it is an independent copy, and remote revocation is out of scope for v1. Stated honestly in user docs; the mitigation is browser-side reset plus the phone's own recovery flow.
Extension uninstalledChrome wipes extension storage. The phone cannot learn this, so the phone's "Linked browsers" surface is a log of link events, not a live device registry and not a revoke control. Copy must say so.
Multiple browsers, profiles, machinesAllowed and unlimited: each link is an independent encrypted copy with its own custody. Chrome profiles are separate vaults. Incognito is unsupported.
Linking with no usable documentThe phone refuses to send until at least one document is registered, with copy explaining why (kills the "empty extension" state).

Open for security review (CEP-12): whether v1 ships key-epoch staleness detection (above) or defers it, given that deferring means a rotated-away identity can still prove from a linked browser until the user resets it.

Non-goals (v1)

  • Document registration in the browser (NFC/KYC stays on mobile).
  • Firefox/Safari, enterprise force-install, multi-device sync, server-side revocation lists. Consequence stated plainly in the post-link lifecycle section: a linked browser cannot be killed remotely, and the phone's linked-browser surface is a log, not a revoke control.
  • Any integration surface for legacy @selfxyz/qrcode/@selfxyz/core: those packages are dead for partners; the hosted page is the only trigger origin.
  • Standalone identity: the extension never registers or recovers an account; no phone, no extension.

Launch gates

  1. Relayer robustness deployed (self-infra PR #166) · CEP-01.
  2. Store CI pipeline green on trusted-tester channel · CEP-02/03.
  3. Security review sign-off (custody, transfer, origin policy, store disclosures) · CEP-12. Blocks public listing. Trusted testers may precede it under an explicit accepted risk: internal team plus test documents only until CEP-12 signs off, external partner testers after. Real identity data does not enter un-reviewed browser custody.
  4. Enterprise-flow dogfood: one real dashboard flow verifying end-to-end through the extension (session, popup, TEE, signed webhook).

Release plan

  1. Internal (unpacked/pinned-key builds): team QA, harnesses in CI.
  2. Trusted testers (store, unlisted channel): every merge auto-publishes; partners we invite.
  3. Public listing: after CEP-12 sign-off; promotion is a manual workflow trigger, still no manual build steps.

PRD-D1 resolved 2026-07-29

Which repo/team owns the Enterprise hosted verification page?

The extension trigger (CEP-09) has to land in the codebase that renders the hosted verification page, so ownership decides where the PR goes and who reviews it.

PRD-D2 resolved 2026-07-29

Store identity: which account publishes the extension?

Whoever owns the Chrome Web Store listing owns publish rights for an identity product; personal accounts are a single point of failure.

PRD-D3 resolved 2026-07-29

Popup scope in v1?

The popup could be disclosure-only or a fuller surface; F4 requires somewhere to select the active proving document.
