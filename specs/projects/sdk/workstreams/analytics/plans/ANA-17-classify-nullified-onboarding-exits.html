Context: a redirect is being misread as dropoff

A user whose document is already registered or nullified is deliberately routed to the recovery flow. The document is fine, nothing broke. But that exit fires no canonical terminal, so today it looks identical to silent dropoff (a crash, a rage-quit). It is not dropoff, it is a hand-off, and the funnel cannot tell the two apart.

What the dashboard should answer

Framing first, before mechanics. The canonical onboarding dashboard answers one primary question:

Where do users drop off on the path to a completed new registration?

Everything else is in service of that. A non-completion has very different meanings, and the dashboard must separate them or the dropoff number lies:

  • Dropoff - user left or something broke in a preceding step. This is the number to drive down. Measured by the gap between consecutive funnel step events.
  • Redirect - app handed the user to recovery (document already in use). Expected, not a leak. Must not count as dropoff to fix.
  • Success - completed a new registration (or recovered a returning identity).

So the terminal is not Failed. It is one Onboarding: Ended event carrying an outcome, where the outcome tells you success vs redirect vs genuine failure. Anything deeper about recovery (did the redirected user actually recover, how long it took) is a separate event suite and dashboard, not this one.

Proposed change: one Onboarding: Ended event with an outcome property

Decision B, locked in. Every attempt resolves to a single terminal event, Onboarding: Ended, carrying an outcome property. The funnel step events are unchanged. No nullifier, no document identifier.

// onboardingFunnel.ts — one terminal, outcome as a property
type OnboardingOutcome = 'completed' | 'recovered' | 'moved_to_recovery' | 'failed';

function endOnboardingAttempt(selfClient, outcome, properties?) {
  const attempt = currentAttempt;
  if (!attempt) return;            // fire-once: one terminal per attempt
  currentAttempt = null;
  if (attempt.isMock) return;
  selfClient.trackEvent(OnboardingEvents.ENDED, {
    ...properties,
    ...baseProperties(attempt),
    outcome,
    duration_seconds: durationSeconds(attempt.startedAt),
    country_code: attempt.countryCode,
    document_type: attempt.documentType,
    used_fallback: attempt.initialBranch !== attempt.currentBranch,
  });
}

completeOnboardingAttempt        -> endOnboardingAttempt(_, 'completed')
recoverOnboardingAttempt         -> endOnboardingAttempt(_, 'recovered')
failOnboardingAttempt(stage, r)  -> endOnboardingAttempt(_, 'failed', { stage, reason: r })
moveOnboardingAttemptToRecovery  -> endOnboardingAttempt(_, 'moved_to_recovery', { stage: 'validating_document' })

// provingMachine.ts — fired once at the account_recovery_choice state, covering both
// the device nullifier check and the server REGISTERED_COMMITMENT redirect
moveOnboardingAttemptToRecovery(selfClient);

Why B

Modularity. If tomorrow we stop counting some ending as "complete," it is an outcome value and a dashboard tweak, not a code change or a new event. Per Mixpanel guidance, variations of one terminal ride a property, not many events.

Decided (not open)

  • Single terminal event. Onboarding: Ended with outcome in {completed, recovered, moved_to_recovery, failed}. The retired Completed / Recovered / Failed constants are deleted in this PR.
  • Redirect is not a failure. outcome: 'moved_to_recovery' is distinct from failed; the dashboard subtracts it from genuine dropoff.
  • Benign recovery is not the tedious recovery. Already-registered-with-the-right-secret is outcome: 'recovered' (returning-user success, lands home). The nullified / other-secret redirect is outcome: 'moved_to_recovery'. The app already routes them to different screens.
  • Detection source is a property, not an outcome. Device nullifier check vs server commitment rejection: stamp detection_source if free at the call site; do not split the outcome for it.
  • Recovery is its own suite. Whether the redirected user recovers, and how long it takes, lives in a separate recovery event family and dashboard - a follow-up ANA item.
  • Stage value: added a precise validating_document member to OnboardingStage.
Every attempt resolves to exactly one terminal. This also closes a side leak: the Sentry cohort-tag clear in app/src/services/analytics.ts now keys off Onboarding: Ended, so the recovery-choice path clears tags too.

Dashboard impact

  • New dashboard, legacy kept. A new canonical dashboard mirrors the old one but terminates on Onboarding: Ended (outcome = completed). The pre-ANA-17 dashboard is renamed with a [legacy] tag and keeps its historical Completed/Recovered/Failed data.
  • Outcome breakdown. Break Onboarding: Ended by outcome and stage, segmentable by initial_branch. Subtract moved_to_recovery from the dropoff number to see the true loss.
  • Per-branch funnels are rebuilt to end on Ended (outcome = completed); the step events themselves are unchanged.

Scope

In scope

  • Add OnboardingEvents.ENDED; route terminals through endOnboardingAttempt(outcome); add moveOnboardingAttemptToRecovery at the account_recovery_choice state. Delete the retired Completed / Recovered / Failed constants.
  • Repoint the Sentry cohort-tag clear to Onboarding: Ended.
  • New canonical dashboard on Ended; legacy-tag the old one.
  • Unit tests: each terminal emits one Ended with the right outcome; the redirect branch emits moved_to_recovery; no PII in payload.

Out of scope

  • The recovery event suite and its dashboard (did the redirected user recover, latency, drop-in-recovery). Separate ANA item.
  • Any nullifier or commitment value in analytics. Stays out, permanently.
  • Backend / on-chain document-level dedup (different system).

Decision: B, locked in

One Onboarding: Ended event with an outcome property, rather than separate Completed / Exit events. Chosen for modularity: re-triaging what counts as "complete" becomes a property and dashboard change, never a new event or code change. Implemented in this PR, bundled with ANA-16 (KYC verdict event) since the two are stacked and touch the same file.
