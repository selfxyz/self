TL;DR

The SDK runs in two modes — self-app (Self Wallet, full UX) and embed (third-party host like Acme, one-shot verification). Today the router doesn't know which mode a route belongs to. ~14 registered routes are pre-built self-app screens awaiting wiring (proof history, receipts, KYC pending/success, points, backup prompt); a smaller set (~5) is genuinely orphan and should be deleted or moved to /dev/*. This workstream defines the routing contract — mode declaration at registration, cluster-owned close, single boot decision, back/close terminology — and a classification backlog. Wiring of self-app pre-builds belongs to WV-13 / WV-14 downstream.

Two modes

Same code base, two consumer surfaces. Most architecture decisions in this workstream hinge on whether a screen is reachable in self-app, in embed, or in both.

self-app mode=self-app

The Self Wallet app. Long-lived, multi-entry. Home, settings, document management, proof history, receipts, points, recovery, backup prompts, account state.

Lifecycle: persistent. User opens, navigates, leaves, returns.

embed mode=embed

SDK invoked from a third-party host (Acme social app, etc.) for one verification. Short-lived. Always terminates via bridge.setResult + bridge.dismiss back to the host. No settings, no history, no home.

Two entry sub-paths, picked at the tour based on local registration state:

  • register + disclose — first-time user, no document registered locally. Full path: tour → KYC → provider → registration proof → disclose → result.
  • disclose-only — returning user, document already registered. Skips KYC: tour → disclose (proof generated against existing registration) → result.

Lifecycle: one-shot. Boots, picks sub-path, completes, dismisses.

shared scope=shared

Screens used by both modes — onboarding flow, NFC capture, recovery phrase input. Mode-aware via useOperatingMode(): terminal behavior differs (self-app: navigate('/'); embed: bridge.setResult + dismiss).

Lifecycle: depends on caller.

The code currently uses wallet / tunnel for these two modes. This spec uses self-app / embed for clarity; the code rename is tracked as NAV-12. Both names refer to the same thing while the rename is in flight.

Why

A full audit of packages/webview-app/src/App.tsx and every screen's navigation calls shows the route graph has accumulated entropy:

No mode tag at registration. Routes don't declare which mode they belong to. Boot enforces it implicitly; the router can't.
Pre-built screens awaiting wiring. ~14 self-app routes (history, receipts, KYC overlays, points, backup) are reachable only via DevRouteMenu. WV-13 / WV-14 will wire them; this workstream classifies them.
True orphans. A small set (/tunnel/registration/* dev sub-flow + a few overlay-shaped routes) should be deleted or refactored into components.
"Back" vs "close". Used interchangeably with no documented difference in intent.
Two boot deciders. ModeBoot + InitialRouteRedirect overlap and can disagree.
Hard-coded close. Cluster terminals call navigate('/') directly — no single owner.
Coupled flows. EU-ID errors route to passport's error screen — accidental, not designed.
Asymmetric namespaces. /tunnel/proof/* vs /proving/* — same engine, different surface.

North Star

A contributor reading any cluster's code can answer in under 30 seconds:

  1. Which mode does this route belong to — self-app, embed, or shared?
  2. Where does this cluster start?
  3. What does "back" do here?
  4. What does "close" do here?
  5. Where does this cluster end on success / cancel / error?

A new route cannot be registered without declaring its mode, picking a namespace, and declaring its close target. Dev-only routes are visibly dev-only at the route level.

Invariants — the durable contract

1

Mode declared at registration

keystone

Every route declares one of: self-app, embed, shared, dev. Declaration lives next to the <Route>, not buried in the screen.

Router fails closed on cross-mode navigation: a self-app boot cannot land on an embed-only route and vice versa.

2

Cluster boundaries

Every route belongs to exactly one cluster (passport, eu-id, aadhaar, self-app-proving, embed-proving, recovery, settings, …). Each cluster declares:

  • One documented entry
  • Ordered internal steps (back walks them)
  • A single close target

Close is owned by the cluster, not the screen.

3

"Back" vs "close"

  • Back — step within the cluster. Never exits.
  • Close — exit the cluster via the cluster's close handler. Never navigate(-1).
  • UI label must match the call. No mixing.
4

Dev-only segregation

Dev-only routes must satisfy all three:

  • Live under /dev/*
  • Registered behind import.meta.env.DEV
  • Linked only from DevRouteMenu
5

One boot decision

Exactly one initial-route function. Inputs:

  • mode from lifecycle.getConfig
  • verificationRequest shape
  • Currently-attempted path

ModeBoot + InitialRouteRedirect collapse into this.

6

Cross-document reuse

Shared UI (NFC error, etc.) is reused via component composition parameterized by document type — never by routing one document's flow into another's route.

7

Namespace structure

Verbs — operations the user is performing:

  • /tour/:step — welcome/education tour
  • /pick-country, /pick-id
  • /capture/{passport,eu-id,aadhaar,kyc}/*
  • /register/{confirm,generating,success,failure}
  • /backup-phrase — first-time backup setup (distinct from /settings/recovery-phrase)
  • /notify — first-time notification opt-in
  • /disclose/{request,review,generating,result,kyc-pending,kyc-success}
  • /recover/{launch,phrase,success,failure,required}

Places — destinations (self-app only):

  • /, /settings/*, /docs, /docs/:id, /history, /receipts/:id, /points/*, /account/*

Dev: /dev/*

No journey prefixes, no mode prefixes. No /onboarding, no /tunnel, no /wallet. Each URL describes one screen / operation. Journey context (am I onboarding? adding a doc? recovering?) lives in code (which navigate() calls happen in what order) and in events (Mixpanel funnels), not in URLs. Cluster-close (NAV-04) is where "after register-success, go to /backup-phrase if first-time, /docs if add-doc" is decided.

8

State-passing slots

  • nextPath — where to go on success
  • backPath — where back goes when history is unreliable
  • returnTo — return after a sub-flow

Mixing slot meanings is not permitted.

9

replace: true

Use it when the user must not be able to back into the screen just left:

  • After terminal outcomes (success/failure)
  • After invalid-state redirects
  • After cluster-internal forward progressions
