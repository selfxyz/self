Why

The embed operating mode is called 'tunnel' in code. Docs, AUDIT, and product conversations all say embed. The mismatch makes onboarding harder and forces every new contributor to learn the translation. NAV-12 renames the operating-mode literal, the screen files, and the bridge-protocol mode value. The bridge does NOT send 'tunnel' across the boundary, so no backwards-compat shim is required for hosts.

Decisions

Locked in on 2026-05-25. See DECISIONS.md.

  • nav-12-q1-mode-literal · Decided

    Rename the literal to 'self-app' | 'embed' or 'wallet' | 'embed'?

    'self-app' | 'embed'. Matches every doc + AUDIT. Larger diff (every 'wallet' usage updates) but the cleanest end state — no doc/code mismatch.

  • nav-12-q2-folder-rename · Decided

    Rename screens/tunnel/ folder + Tunnel* file/class names in this PR, or split?

    All in one PR. Folder rename + every file/class + every importer. Single coherent diff, no inconsistent intermediate window.

Scope

  • Rename OperatingMode literal to 'self-app' | 'embed' in both definition sites (per decision q1). Update every consumer.
  • Rename screens/tunnel/ → screens/embed/, every Tunnel* file/class to Embed*. Update imports. Single PR (per decision q2).
  • Update DevRouteMenu labels ("Tunnel — Screens" → "Embed — Screens", etc.).
  • Update tests (tests/screens/tunnel/* renames + import updates).
Route paths are out of scope. The /tunnel/* → new-namespace rewrite belongs to NAV-08. NAV-12 is code-only (mode literal + screen names + bridge type).

Out of Scope

  • Route path renames — NAV-08.
  • No bridge protocol changes. The bridge does not send the mode literal across; getConfig's response value is owned on both sides. Renaming the constant on both sides is enough.
  • No CHANGELOG/release notes beyond noting "internal rename, no host-facing changes."

Approach

Step 1 — Mode literal

Rename OperatingMode in both definition sites to 'self-app' | 'embed' per decision q1. Run TS compiler to surface every consumer; fix mechanically.

Step 2 — Bridge contract sanity check

Open packages/webview-bridge/src/adapters/lifecycle.ts and the getConfig handler in the RN side. Confirm the mode value flows through as an opaque string; both sides need to flip simultaneously. Document this in packages/webview-bridge/README or equivalent.

Step 3 — File and folder renames (decision q2: all in one PR)

Use git mv for clean history:

git mv packages/webview-app/src/screens/tunnel packages/webview-app/src/screens/embed
# Rename files within:
git mv .../embed/TunnelTourScreen.tsx .../embed/EmbedTourScreen.tsx
# ... 10 more files ...

Then sed/rename inside files. Update App.tsx imports and DevRouteMenu entries.

Step 4 — Spec updates

Where SPEC.html and AUDIT.html prose says "tunnel mode" or "tunnel screens," update to "embed." Route paths in prose stay as /tunnel/* because the actual routes haven't moved yet (NAV-08).

Validation

  • grep -rn "'tunnel'\|\"tunnel\"" packages/ app/ — zero hits (except in NAV-08-owned route strings).
  • grep -rn "Tunnel[A-Z]" packages/webview-app/src — zero hits.
  • yarn types && yarn build && yarn lint across all packages — clean.
  • Manual: launch the dev server with ?mode=embed — flow boots into embed mode. Old ?mode=tunnel URL returns the catch-all (or temporarily aliases per host shim, if added).
  • RN test suite passes: packages/rn-sdk/__tests__/LifecycleHandler.test.ts.
