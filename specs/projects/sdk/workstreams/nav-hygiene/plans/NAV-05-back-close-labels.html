Why

Per SPEC invariant #3: back walks the user backward in the cluster's local history; close ends the cluster (home in self-app, setResult+dismiss in embed). Today the code conflates these. onClose sometimes does navigate(-1) (back), sometimes navigate('/') (close). Handler names span 11 patterns — onClose, onDismiss, handleClose, handleDismiss, handleBack, onBack, onEscape, onCancel, … NAV-05 sweeps every screen, aligns handler-name + semantics, and replaces ad-hoc close logic with useClusterClose() from NAV-04.

Decisions

Locked in on 2026-05-25. See DECISIONS.md.

  • nav-05-q1-handler-names · Decided

    Standardize handler names AND semantics, or only enforce semantics?

    Standardize both. Canonical set: handleClose, handleBack, handleRetry, handleContinue. Every screen renames.

  • nav-05-q2-eslint-rule · Decided

    Custom ESLint rule, or rely on review + AGENTS.md?

    Ship a custom ESLint rule. Lives at packages/webview-app/eslint-rules/handler-names.js. AGENTS.md still documents the rule for humans.

Naming convention to enforce

IntentLocal handler nameImplementation
Cluster-exit (close the flow, mode-aware)handleCloseuseClusterClose() from NAV-04
Walk back one step in local historyhandleBacknavigate(-1) (or navigate(state.backPath) when explicit)
Retry the current attempt (in place)handleRetryscreen-specific re-attempt
Continue to next stephandleContinuenavigate(nextPath)

Banned names: onDismiss, onCancel, onEscape, handleDismiss, handleCancel (as local handler names). Euclid prop names are unchanged — we control only what we name our callbacks.

Scope

  • Sweep every screen in packages/webview-app/src/screens/ (~50 files).
  • For each handler that walks back, rename to handleBack; implement via navigate(-1) or explicit state.backPath.
  • For each handler that exits the cluster, rename to handleClose; implement via useClusterClose().
  • For each handler that retries, rename to handleRetry.
  • For each handler that advances, rename to handleContinue (when target is variable) or a descriptive name (when target is fixed, e.g. handleStartProving).
  • Add to packages/webview-app/AGENTS.md a "Handler naming conventions" section enumerating the table above.
  • Add a custom ESLint rule at packages/webview-app/eslint-rules/handler-names.js that flags banned local-handler names (onDismiss, handleDismiss, onCancel, handleCancel, onEscape) in src/screens/**/*.tsx. Auto-fixer maps to the canonical name where the intent is unambiguous; otherwise the rule emits a hint and leaves the rename to the developer.

Out of Scope

  • No Euclid changes. Euclid component prop names (onClose, onDismiss, onTryAgain) are not ours to rename.
  • No new shared header component. AUDIT confirms one doesn't exist; building one is a separate scope (Euclid territory).
  • No URL-label changes ("back" or "close" in the URL — none exist today; we operate on handler names + UI strings).
  • No bridge changes.

Required Files

Approach

Step 1 — Generate the per-screen audit table

Use the research already in AUDIT.html. Produce a table with one row per screen × handler: current name, new name, new implementation.

Step 2 — Mechanical renames

For each screen, rename the local handler. Update the body so the implementation matches the intent. Example:

// Before
const onClose = useCallback(() => { navigate(-1); }, [navigate]);
// inside JSX: <EuclidScreen onClose={onClose} />

// After (the handler does "back," so rename + Euclid prop wiring is just `onClose={handleBack}`)
const handleBack = useCallback(() => { navigate(-1); }, [navigate]);
// <EuclidScreen onClose={handleBack} />

Euclid prop stays onClose; the wire makes the intent explicit because the local handler name says "back."

Step 3 — Cluster-exit handlers route through NAV-04

// Before
const handleDismiss = useCallback(() => { navigate('/', { state: { skipOnboardingRedirect: true } }); }, [navigate]);

// After
const handleClose = useClusterClose();
// <EuclidScreen onDismiss={handleClose} />

If useClusterClose's default close target loses the skipOnboardingRedirect state, NAV-09 (state-passing) will define how to pass it through; for NAV-05, this is documented as a known limitation.

Step 4 — Documentation

Add to packages/webview-app/AGENTS.md:

Handler naming: handleClose = cluster-exit via useClusterClose(); handleBack = navigate(-1) or navigate(state.backPath); handleRetry = re-attempt; handleContinue = advance. Do not use onDismiss, onCancel, or handleDismiss as local handler names — those words only exist on Euclid props.

Validation

  • grep -rn "const onDismiss\|const handleDismiss\|const onCancel\|const handleCancel" packages/webview-app/src/screens — zero matches.
  • grep -rn "const onClose" packages/webview-app/src/screens — only when followed by a useClusterClose() call (and even then prefer handleClose).
  • yarn types && yarn build — clean.
  • Manual: every cluster terminal screen, close behavior is correct in both modes.
  • Manual: every back-button takes the user one logical step backward (no surprise jumps to home).
