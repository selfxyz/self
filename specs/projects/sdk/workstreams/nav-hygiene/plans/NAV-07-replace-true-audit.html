Why

SPEC invariant #9: use replace: true when the user must not be able to back into the screen just left — after terminal outcomes, invalid-state redirects, and cluster-internal forward progressions. Today: 194 navigate() calls, 44 explicit replace: true, 150 default-replace. Audit identifies 5 specific violations (terminal handlers missing replace: true). NAV-07 fixes those, documents the rule, and decides on automation (custom ESLint rule vs. docs only).

Decisions

Locked in on 2026-05-25. See DECISIONS.md.

  • nav-07-q1-eslint-rule · Decided

    Custom ESLint rule, or AGENTS.md docs?

    AGENTS.md docs only for this rule. The "is this a terminal handler" signal is too heuristic to enforce mechanically without high false-positive noise. (NAV-05 ships an ESLint rule for handler-names — that rule is name-driven and much more reliable.)

  • nav-07-q2-audit-scope · Decided — upgrades scope

    Fix only the 5 known violations, or full sweep of all 150 default-replace calls?

    Full sweep. Walk every navigate() call without an explicit replace. Classify each: terminal → add replace:true; forward progression → audit per case; modal/wizard → leave default. Estimate: 2–3 hours, ~5–10 additional violations beyond the named 5.

    This is the non-recommended option — Scope below expands accordingly. If the sweep snowballs (>20 violations or unclear cases), split off a NAV-07-followup plan rather than blocking the named-5 fixes.

Scope

  • Fix the 5 known violations (named in Findings).
  • Full sweep of the remaining 145 default-replace calls per decision q2. Produce a per-call classification table (terminal / invalid-state / forward / wizard / modal). Add { replace: true } wherever the call matches a terminal, invalid-state, or cluster-internal forward pattern.
  • Document the rule in packages/webview-app/AGENTS.md (invariant #9 wording + 2–3 worked examples) per decision q1.
  • If the sweep surfaces >20 ambiguous cases, split a follow-up plan (NAV-07b) and ship the unambiguous fixes in this PR.

Out of Scope

  • No new tests. replace: true behavior is a router-internal property; unit-testing it screen-by-screen is not worth the toil.
  • No changes to react-router or any provider.
  • No restructuring of navigate calls beyond adding the { replace: true } option to the 5 (or 5-15) flagged calls.

Approach

Step 1 — Fix the 5 named violations

Mechanical edits. One line each. PR diff: ~5 LOC. Ship this even if Step 2 stalls.

Step 2 — Full sweep (per decision q2)

Walk every navigate() call in packages/webview-app/src that omits the replace option. For each, classify and act:

PatternAction
Terminal handler (handleClose, onSuccess, onFailure, etc.)Add { replace: true }
Invalid-state redirect (effect bouncing users out of an inconsistent route)Add { replace: true }
Cluster-internal forward progression where the prior step is no longer meaningfulAdd { replace: true }
Wizard / multi-step where back-tracking IS expectedLeave default
Modal / detail navigation that the user may legitimately back out ofLeave default

Track every call's classification in the PR description so reviewers can audit the judgments. If >20 calls fall in an ambiguous bucket, defer them to a NAV-07b follow-up rather than guessing.

Step 3 — Document the rule

Add to packages/webview-app/AGENTS.md:

Replace semantics. Use navigate(path, { replace: true }) when the user must not be able to back into the screen they just left: (1) after terminal outcomes — success, failure, kyc-pending; (2) after invalid-state redirects — e.g. HomeScreen sending no-document users to onboarding; (3) on cluster-internal forward progressions where the prior step is no longer meaningful. Default replace: false is correct for ordinary forward navigation.

Validation

  • cd packages/webview-app && yarn build && yarn lint && yarn types — clean.
  • Manual: from each of the 4 named-violation screens, complete the success path, then press the browser back button → the user is NOT returned to the success screen.
  • Manual spot-check of 3–5 randomly sampled screens from Step 2's classification table to confirm back behavior matches the classification.
  • Sweep audit table (in the PR description) covers every navigate() call without explicit replace; each row has a classification + decision.
