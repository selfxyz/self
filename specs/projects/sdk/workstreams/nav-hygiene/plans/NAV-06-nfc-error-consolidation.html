Why

Passport has /onboarding/passport/nfc-error + /onboarding/passport/nfc-success. Aadhaar has /onboarding/aadhaar/upload-error + /onboarding/aadhaar/upload-success. EU-ID has only the success route — it navigates to passport's error route from two call sites. The borrowed route's UI, strings, and analytics names are passport-specific, so EU-ID users see "passport" copy on their NFC errors.

Decisions

Locked in on 2026-05-25. See DECISIONS.md.

  • nav-06-q1-split-vs-param · Decided

    Split routes per document, or parameterize the Euclid NfcErrorScreen?

    Split. EU-ID gets its own /onboarding/eu-id/nfc-error route, mirroring the Aadhaar precedent. File an Euclid follow-up ticket for an upstream EuIdNfcErrorScreen component if one doesn't exist yet.

Euclid coupling

PassportNfcErrorScreen (from @selfxyz/euclid) is passport-specific: hardcoded strings, analytics events like passport_scan_start_over. It does NOT accept a documentType prop today.

Scope

Per Q1 (split-routes vs param-euclid). Recommended path: split-routes.

  • Add EU-ID-specific routes in App.tsx:
    • /onboarding/eu-id/nfc-error → <EuIdNfcErrorRoute />
    • (If symmetric: also confirm /onboarding/eu-id/nfc-success exists; it does — line 115)
  • Create screens/onboarding/eu-id/EuIdNfcErrorRoute.tsx as a thin wrapper around an Euclid component (or a local EU-ID-flavored copy of PassportNfcErrorScreen). The wrapper reads location.state in the same shape passport's does: { countryCode?, errorMessage?, stage? }.
  • Update the two EU-ID call sites to navigate to the new EU-ID route: 
    navigate('/onboarding/eu-id/nfc-error', { state: ..., replace: true });
  • If Euclid doesn't have an EU-ID NFC error component, this plan creates the wrapper locally and TODOs an Euclid migration — call out in Hand-off.
  • Keep passport's route and screen unchanged.

Out of Scope

  • No changes to the passport flow.
  • No Aadhaar changes. Aadhaar already has its own routes.
  • No Euclid library changes. If an EU-ID error component is needed, this plan creates a local wrapper that renders the closest Euclid component or a local React component. Euclid changes are a follow-up.
  • No analytics-event consolidation. Per-document analytics (e.g. passport_scan_start_over vs eu_id_*) stay distinct.

  • packages/webview-app/src/App.tsx (register /onboarding/eu-id/nfc-error)

Approach

Step 1 — Identify the Euclid component to wrap

Check @selfxyz/euclid for an EU-ID-specific NFC error screen. If none exists, decide between:

  • Reusing PassportNfcErrorScreen with EU-ID copy overrides via props (if Euclid exposes them — currently doesn't).
  • Authoring a small local EU-ID copy of the screen until Euclid catches up. Flag this in Hand-off.

Step 2 — Create the route component

Pattern follows PassportNfcErrorRoute (the existing wrapper):

// EuIdNfcErrorRoute.tsx (sketch)
export function EuIdNfcErrorRoute() {
  const location = useLocation();
  const { countryCode, errorMessage, stage } = (location.state ?? {}) as {
    countryCode?: string; errorMessage?: string; stage?: 'mrz' | 'nfc';
  };
  // Render Euclid component or local copy with EU-ID copy + analytics
  return <EuIdNfcErrorScreen ... />;
}

Step 3 — Register and re-point

Add <Route path="/onboarding/eu-id/nfc-error" element={<EuIdNfcErrorRoute />} /> in App.tsx near other EU-ID routes (around line 110-115).

Update the two navigate sites to target the new route.

Step 4 — Dev menu

Add EU-ID error entry to DevRouteMenu.tsx under the EU-ID group.
