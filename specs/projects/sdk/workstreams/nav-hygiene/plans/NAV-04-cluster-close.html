Why

"Close" means different things in different clusters and different modes. In self-app mode, closing the proving flow lands on home; in embed mode, the same action must call bridge.setResult + bridge.dismiss. Today this is ad-hoc: 6 screens hardcode navigate('/'), 8 screens call lifecycle.dismiss() directly, recovery uses state.returnTo. NAV-04 introduces a single useClusterClose() hook backed by a per-cluster registry that handles mode-aware close in one place.

Decisions

Locked in on 2026-05-25. See DECISIONS.md for the workstream-wide record.

  • nav-04-q1-cluster-detection · Decided · Plus follow-up

    How does useClusterClose() know which cluster the caller belongs to?

    Infer from useLocation().pathname's first segment. Plus: state-of-the-art review + a test that proves no screen is reachable through two paths (see Approach Step 1.5).

    "I picked A, but can you investigate what the state of the art is? wouldnt that be possible to do A and to make sure in the tests or somewhere that none of the screens are going to be reachable through 2 paths?" Approach grows a sub-step: brief react-router-dom v6 / Next-app-router segment-API survey, plus a registered-routes invariant test that fails if any screen component is the element of more than one <Route>, or if any path's first segment maps to multiple clusters.

  • nav-04-q2-default-close-target · Decided

    Default self-app close target: always navigate('/'), or per-cluster entry points?

    Per-cluster entry point in the registry. Each cluster declares its own "close lands here" path; / stays the default only for clusters that genuinely have nowhere better to land.

  • nav-04-q3-overrides · Decided

    Should screens override the close target at call time (via state.returnTo), or only via the registry?

    Hook respects state.returnTo (will become state.nextPath after NAV-09). Matches the existing recovery pattern.

Approach

Step 1 — Define the cluster enum and registry (with per-cluster entry points)

Enumerate every cluster currently in screens/. Each gets a CloseTarget entry with a meaningful self-app landing path (per decision q2):

const CLUSTER_CLOSE: Record<Cluster, CloseTarget> = {
  home:       { selfApp: '/',         embed: 'dismiss-only' },
  onboarding: { selfApp: '/',         embed: { result: { success: false, error: 'user_cancelled' } } },
  docs:       { selfApp: '/docs',     embed: 'dismiss-only' },
  proving:    { selfApp: '/',         embed: { result: { success: false, error: 'user_cancelled' } } },
  disclose:   { selfApp: '/history',  embed: { result: { success: false, error: 'user_cancelled' } } },
  recovery:   { selfApp: '/settings/security', embed: 'dismiss-only' },
  settings:   { selfApp: '/',         embed: 'dismiss-only' },
  points:     { selfApp: '/',         embed: 'dismiss-only' },
  account:    { selfApp: '/',         embed: 'dismiss-only' },
  ...
};

The per-cluster landing paths are the canonical answer to "where does the user expect to be after closing this flow?". Recovery successes land back on the security settings page; document closes land on the document list; everything else falls back to home.

Step 1.5 — Cluster-detection state-of-the-art + dual-path invariant test

Decision q1 chose path-segment inference plus a guarantee that no screen is reachable via two paths. The plan adds:

  • State-of-the-art brief. Document the survey in packages/webview-app/AGENTS.md ("Cluster detection") so future contributors don't re-explore this:
    • react-router-dom v6 exposes no first-class cluster API. The common patterns are: (a) inspect useLocation().pathname.split('/')[1] like we do; (b) wrap every route in a context provider that injects the cluster name; (c) use useMatches() after defining a typed handle on each route. (a) is the smallest hammer.
    • Next.js app-router has useSelectedLayoutSegment() / useSelectedLayoutSegments() — which is precisely "first path segment" plus pre-defined parallel-route boundaries. Confirms that path-segment is the canonical signal.
    • NAV-13's ModeRoute already needs a per-route metadata pass; if a cluster slot were added there (<ModeRoute cluster="recovery" ... />), useClusterClose could read it instead. Deferred — only needed if path-segment inference ever fails the invariant test below.
  • Dual-path invariant test. Add packages/webview-app/tests/routes/clusterInvariant.test.tsx that imports the route table from App.tsx (after extracting it into src/routes.tsx if needed) and asserts:
    1. Every screen component appears as the element of at most one <Route>. Failing test ⇒ two paths render the same component ⇒ the cluster-segment trick can be wrong.
    2. For every registered path, pathname.split('/')[1] maps to at most one cluster (per the CLUSTER_CLOSE keys). Failing test ⇒ two clusters share a first segment ⇒ ambiguity.
  • Extract the registered routes into src/routes.tsx (a typed array) so the test can introspect them without rendering. App.tsx maps the array to JSX.

Step 2 — Implement the hook

function useClusterClose(overrideCluster?: Cluster): () => void {
  const navigate = useNavigate();
  const location = useLocation();
  const { mode } = useOperatingMode();
  const { lifecycle } = useSelfClient();

  return useCallback(() => {
    const cluster = overrideCluster ?? inferClusterFromPath(location.pathname);
    const target = CLUSTER_CLOSE[cluster];

    if (mode === 'tunnel') {
      if (target.embed !== 'dismiss-only') {
        lifecycle.setResult(target.embed.result).catch(() => {});
      }
      lifecycle.dismiss({ reason: 'user_cancel' });
      return;
    }

    // self-app: state.returnTo overrides the registry entry (decision q3)
    const stateReturn = (location.state as { returnTo?: string } | null)?.returnTo;
    navigate(stateReturn ?? target.selfApp, { replace: true });
  }, [mode, location.pathname, location.state, lifecycle, navigate, overrideCluster]);
}
