Most "unreachable" routes are pre-built self-app screens awaiting WV-13 / WV-14 wiring — not deletion candidates. Two entry sub-paths, chosen at the tour based on local registration state:

  • register + disclose (purple) — first-time user. Full path through KYC, provider, registration-proof generation, then disclose.
  • disclose-only — returning user. Skips KYC entirely; goes straight from tour to disclose (proof generated internally against the existing registration).

Both paths converge at /disclose/review and terminate via bridge.setResult + bridge.dismiss. Account-recovery is a third side-entry available from the tour. KYC review hold: if Didit returns a "review pending" result, the user lands on /disclose/kyc-pending with the option to dismiss (host session ends, review continues async); when review clears asynchronously the user resumes by re-entering and lands on /disclose/kyc-success.

Findings By Category

No mode classification at route registration

High severity

Routes don't declare which mode they belong to. ModeBoot redirects between mode roots, but the router can't reject a cross-mode navigation (e.g. an embed flow trying to reach /settings). Mode coupling is implicit and scattered across screen guards and provider effects.

NAV-01 NAV-13

Self-app pre-builds awaiting wiring (~9)

Medium severity

Pre-built self-app screens reachable only via DevRouteMenu — Self Wallet pieces that haven't been hooked into production navigation yet:

  • Proof artifacts: /proving/history, /proving/receipt, /proving/generation-success, /proving/backup-prompt, /proving/kyc-pending, /proving/kyc-success
  • Account: /account/verified
  • Points: /points, /points/invite

These are not orphans. Classification (NAV-01) feeds WV-13 (proof overlays + history) and WV-14 (home + document management) which do the actual wiring.

NAV-01 WV-13 WV-14

Deferred for v1: social sign-on placeholders (3)

Low severity

/onboarding/backup, /onboarding/signin, /onboarding/conflict — Euclid screens are not built yet (TODO WV-12), so wiring is deferred for v1. Routes stay registered with placeholder content, reachable only via DevRouteMenu, and are excluded from the v1 production graph. Triage classifies all three as defer. Reopen when WV-12 lands.

NAV-11 WV-12

True orphans (~4)

Medium severity

Routes with no plausible production purpose:

  • /tunnel/registration/country + /tunnel/registration/id-type — dev sub-flow that bypasses KYC entirely. Delete or move to /dev/*.
  • /proving/dialogue, /dialogue-cta, /generation-dialogue — overlay-shaped. Likely belong as components, not routes.
  • /debug/keychain — already correctly DEV-gated (the pattern NAV-02 standardizes).

NAV-01 NAV-10

Boot decision overlap

High severity

Two functions decide initial route:

  • ModeBoot — redirects on mode + verificationRequest shape.
  • InitialRouteRedirect — wildcard * catch-all, redirects on URL params.

Both can fire on the same boot. Their outputs sometimes agree and sometimes don't.

NAV-03

Cluster terminal screens hard-code navigate('/')

High severity

Every NFC success, Aadhaar success, KYC failure screen calls navigate('/') directly. No single owner of "what does close mean for cluster X."

Problem worse in shared clusters (NFC, recovery): they must close differently in self-app (→ /) vs embed (→ bridge.dismiss). Currently each screen branches on useOperatingMode(). NAV-04 funnels through one cluster-owned handler.

NAV-04

"Back" vs "close" inconsistency

Medium severity

Sample of the inconsistency:

  • Passport instructions: "close" calls navigate(-1) (steps back inside cluster — should be "back").
  • Passport NFC success: "close" calls navigate('/') (cluster exit — correct).
  • Notifications: "close" calls navigate(-1) back to recovery phrase (within-cluster — should be "back").
  • EU-ID instructions: "close" calls navigate(-1) to ID-select (cluster exit but routed as back).

NAV-05

Cross-document coupling (EU-ID → passport error)

Medium severity

EU-ID flows reuse /onboarding/passport/nfc-error for both MRZ and NFC errors. EU-ID has its own /onboarding/eu-id/nfc-success — no matching reuse for success. Asymmetry suggests accidental, not designed.

NAV-06

replace: true inconsistency

Medium severity

Most cluster-internal forward progressions use replace: true. Most "close to home" actions don't. Exceptions in both directions. No documented rule.

NAV-07

Namespace asymmetry

Low severity

Self-app proving: /proving/*. Embed proving: /tunnel/proof/*. Same engine, both instantiate the same provingMachine. After NAV-12 rename, target is /self-app/proof/* vs /embed/proof/* (or simply /app/proof/*).

NAV-08 NAV-12

Methodology

Four parallel agent sweeps:

  1. Self-app onboarding (tour → country → ID select → document flows → outcomes)
  2. Embed flow (boot → tour → KYC → proving → disclose → result)
  3. Proving / recovery / settings (self-app ?disclosures path, /recovery/*, /settings/*)
  4. Entry / boot redirects (ModeBoot, InitialRouteRedirect, wildcard catch-all)

Each sweep traced every useNavigate, <Navigate>, route param, and state field. Edges are verified against code, not inferred from naming.

Regeneration

  1. Re-run the four parallel sweeps against the updated code.
  2. Update the mermaid blocks above.
  3. Update the route list in ROUTES JS array.
  4. After NAV-01, "uncategorized" count should reach zero; after NAV-13, every route should have a declared mode in code.
