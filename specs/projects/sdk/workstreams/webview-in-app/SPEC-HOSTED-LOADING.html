Scope

The RN host loads the WebView from an embedded bundle at app install time. The build-pipeline (BP-01, done) copies the latest @selfxyz/webview-app dist into packages/rn-sdk/assets/self-wallet/, which gets bundled into the host's iOS .ipa / Android .apk. This matches what packages/native-shell-android/ and packages/native-shell-ios/ currently do, and is consistent with the existing rn-sdk-test-app integration.

Hosted HTTPS URL loading from verify.self.xyz is a future evolution under the sdk-distribution/ workstream; it is not the v1 mechanism for Self app because (a) embedded bundles avoid offline-first-launch friction, (b) HTTPS introduces a single point of failure if the CDN goes down, and (c) WebView caches across hosted deploys are out of our control.

This spec covers WIA-09.

In scope

  • The production URL contract.
  • The coupling between the RN binary version and the WebView protocol version it supports.
  • The dev-server override pattern.
  • Offline / first-launch behavior.
  • Loading-latency UX (splash → ready handoff).
  • Sentry instrumentation for load failures.

Out of scope

  • Hosting infrastructure for verify.self.xyz — owned by sdk-distribution/. This spec consumes the URL; it does not specify the CDN, TLS, or caching policy.
  • The bundle build pipeline that produces the artifact behind that URL — owned by build-pipeline/ (BP-01, done).
  • The bridge protocol itself — owned by packages/webview-bridge/. Version handshake belongs to it; this spec defers to it.
  • Embedded-bundle fallback. Considered as a follow-up under "Known Gaps"; not part of v1.

Decisions

  1. The WebView loads from an embedded bundle. Android: file:///android_asset/self-wallet/index.html. iOS: ${mainBundlePath}/self-wallet/index.html, falling back to the relative path self-wallet/index.html when the bundle path is unavailable. The verification request is appended as a query string on the source URL. The bundle is produced by @selfxyz/webview-app build and copied into packages/rn-sdk/assets/self-wallet/ by the build-pipeline (BP-01, done).
  2. Each Self app release is paired with a webview-app build. The bundle is frozen at app build time. Updating the WebView requires shipping a new RN binary release — no OTA. The app-version constant in the RN host's release notes carries the webview-app commit it was built against.
  3. devServerUrl is the only override, and it is __DEV__-gated. Production builds compile the dev path out entirely. Engineers working locally pass devServerUrl="http://localhost:5173" (or their dev box's IP); release binaries ignore the prop.
  4. Loading UX is splash + spinner up to 3 seconds. Past 3s the splash transitions to a "still loading" state. Past 10s without lifecycle.ready, the host shows a recoverable error with a retry button. A hard WebView load failure (onError / onHttpError / Android onRenderProcessGone) fails fast into the same recoverable-error state rather than waiting out the 10s timer. The 3s / 10s thresholds match the bridge host's invariant in SPEC-BRIDGE-HOST.
  5. Version mismatch fails closed; recover when recovery is possible, dead-end only when it isn't. The bridge envelope carries a single integer version field. BRIDGE_PROTOCOL_VERSION (defined in webview-bridge, currently 1) is the single source of truth for that number; the host imports it rather than copying it. The host enforces the contract on every inbound bridge message: it checks the envelope version by exact equality and rejects (never dispatches) anything that does not match — including a missing or non-numeric version (default-deny). What the user sees depends on whether recovery is possible:
    • A present-but-wrong version (e.g. the bundle says 2, the host expects 1) is a definitive incompatibility — reloading the frozen bundle mismatches identically, so a retry is futile. The host shows a terminal "Please update Self app" state with no retry button; a dead button is worse than honest finality.
    • A missing or non-numeric version is more likely a transient/malformed frame than a stale binary, so the host shows the recoverable error state with retry — the same surface as a load timeout.
    Either way the message is rejected and a Sentry exception is captured; the host never attempts a best-effort downgrade. The WebView side enforces the same constant independently on the messages it receives.
  6. Hosted URL loading is a future evolution, not v1. When and if we want OTA-style updates without app store cycles, the sdk-distribution/ workstream wires verify.self.xyz/v1/ as an alternative source. The bridge protocol and the host shell stay identical; only the source prop on the WebView changes. This spec does not block on that evolution.

  │    Shell → App: show recoverable error screen (fast, no 10s wait)
  ├─ 10s elapsed, no ready
  │    Shell → Sentry: captureException(webview_load_timeout)
  │    Shell → App: show recoverable error screen + retry
  ├─ inbound envelope version present but != BRIDGE_PROTOCOL_VERSION (any message, incl. ready)
  │    Shell: exact-equality check fails → UNSUPPORTED_VERSION reply to WebView + onVersionMismatch
  │    Shell → Sentry: captureException(webview_version_mismatch)
  │    Shell → App: show TERMINAL "Please update Self app" (no retry — reload is futile)
  └─ inbound envelope version missing / non-numeric (any message)
       Shell: reject (fail closed) → UNSUPPORTED_VERSION reply to WebView + onVersionMismatch
       Shell → Sentry: captureException(webview_load_error)
       Shell → App: show RECOVERABLE error screen + retry (likely transient)

Invariants

  1. Production builds load only the embedded bundle. The devServerUrl prop is gated on __DEV__ and compiled out of release builds entirely — a malicious or accidental prop in production has no effect.
  2. Every failure the host reports carries enough context to diagnose without a breadcrumb trail: the diagnostic event names the failure kind (timeout / load error / version mismatch) and the source (bundle vs dev-server). The host imports no error reporter and keeps no breadcrumb stack of its own — diagnostics are injected by the consumer.
  3. The host has no logic that depends on the WebView's internal route table. The bundle is an opaque entry point.
  4. First-launch failures (corrupt bundle, asset-bundling misconfiguration) surface as user-actionable errors with a retry, not silent crashes — fast via onError where the platform reports it, and via the 10s timeout as the backstop.
  5. The Sentry exception captured on any load failure carries the runtime: rn-host tag and a webview_source tag identifying bundle vs dev-server source.
  6. A present-but-wrong version is terminal: the host offers no retry, because reloading the same frozen bundle would mismatch identically (a retry button that can't work is worse than honest finality). A missing/non-numeric version, a load timeout, and a hard load error are all recoverable and expose retry.
  7. The single source of truth for the protocol version number is BRIDGE_PROTOCOL_VERSION, defined in webview-bridge and imported — never copied — by the host. The host enforces it by exact equality on every inbound message and rejects any non-matching or absent version (fail closed). A present-but-wrong version surfaces the terminal upgrade state; a missing/non-numeric version surfaces the recoverable error state. The WebView side enforces the same constant independently.

Known gaps

  • WebView updates require app-store cycles. With the embedded bundle model, a UI-only WebView change ships only when a new RN binary is released. If iteration speed becomes a constraint, the hosted-URL evolution (Decision 6) is the answer.
  • Cohort-targeted WebView builds. A/B testing the WebView in v1 requires shipping multiple RN binaries (per-cohort builds), which is impractical. Defer to the hosted-URL evolution when this becomes a real need.
  • Bundle size. The embedded WebView bundle adds to the app's install size. If install-size pressure becomes a concern, the hosted-URL evolution shrinks the binary at the cost of a network dependency on first launch.

Cross-workstream coordination

  • build-pipeline/ owns the bundle artifact under packages/rn-sdk/assets/self-wallet/ (BP-01, done). Any change to the bundle layout requires coordinated updates in this spec.
  • sdk-distribution/ owns the future hosted-URL evolution (Decision 6). Not active in v1.
  • webview-bridge/ owns the BRIDGE_PROTOCOL_VERSION constant and enforces exact equality on the WebView side in its schema. The host imports the same constant and enforces it independently on the messages it receives. Any bump is a coordinated breaking change: the host binary and the bundled webview-app must move together, since both sides fail closed on any envelope whose version differs or is absent. This spec consumes the constant; it does not define the number.

Validation

  • Production build, airplane mode → bundle loads fine (no network dependency); splash hides within 3s on a regression test device.
  • Production build with a missing / corrupted index.html → the WebView fires onError and the recoverable error screen appears fast (not after the 10s backstop); no crash; the injected diagnostic fires with kind: 'load_error' and the bundle source.
  • Dev build with devServerUrl="http://localhost:5173" → loads localhost. Stop the dev server → "still loading" state at 3s, error at 10s (or sooner via onError), retry restores load.
  • Synthetic devServerUrl in a release build → prop ignored, embedded bundle loads (because the dev code path is compiled out).
  • Synthetic version mismatch (host pinned to BRIDGE_PROTOCOL_VERSION = 1, bundle emits an envelope with version: 2) → terminal "Please update Self app" screen with no retry button; Sentry exception webview_version_mismatch captured with runtime: rn-host + webview_source tags.
  • Synthetic missing version (bundle emits an envelope with no version field) → the message is still rejected (fail closed), but the user sees the recoverable error screen with retry, not the terminal upgrade screen — an absent version is treated as a likely-transient malformed frame, not a definitive incompatibility.
