Overview

You are finishing WIA-09. The embedded-bundle source, __DEV__-gated devServerUrl, the loading → slow → failed → ready state machine, the lifecycle.ready → splash-dismiss handoff, and retry already shipped in packages/rn-sdk/src/SelfVerification.tsx. This plan covers only the remaining work: the version handshake (terminal on a present-but-wrong version, recoverable on a missing one), fast-fail on hard WebView errors, injected diagnostics, analytics funnel events, and replacing the inline overlay with consumer-supplied (Euclid) UI.

Contract lives in Bundle Loading & Versioning (the what — decisions, invariants, backlog). This page is the how — file paths and fire sites for one PR. Branch: feat/webview-in-app.

Locked decisions (do not re-litigate)

  • Version mismatch fails closed at dispatch; UX recovers when it can. Exact equality against BRIDGE_PROTOCOL_VERSION — any non-matching or missing/non-numeric version is rejected, never dispatched. A present-but-wrong number → terminal upgrade screen, no retry (reloading the frozen bundle mismatches identically, so a retry button would be a dead button). A missing/non-numeric version → the recoverable error state with retry (most likely a transient malformed frame, not a stale binary). Don't trap the user behind a dead-end for something a retry might fix.
  • Diagnostics are injected, never imported. rn-sdk must NOT add @sentry/react-native. The host fires an optional reporter callback; the Self app wires it to Sentry. This matches the existing analytics?: AnalyticsSink injection.
  • Error UI is a render-prop with a local-palette default. rn-sdk exposes renderLoading / renderError slots; the Self app passes Euclid (0.x RN) screens. rn-sdk has exactly one dependency (@selfxyz/webview-bridge) and no design-token package, and must NOT add Euclid — so the built-in default cannot consume "shared" tokens. Instead, the default reads from a single local palette constant defined in rn-sdk (Task 5), replacing the scattered raw-hex strings. The render-prop is the path for branded/tokenized UI; the local default exists only so consumers that pass nothing still get a non-broken screen.

Out of scope

  • You will NOT add @sentry/react-native or @selfxyz/euclid to packages/rn-sdk/package.json.
  • You will NOT change the hosted-URL / OTA story (declined — see Bundle Loading spec Decision 6 and the workstream sdk-distribution/).
  • You will NOT touch the webview-app (WebView-side) error screens — the host overlay renders when the WebView is unavailable and cannot use them.
  • You will NOT alter the 3s / 10s thresholds.

Task 1 — Single source of truth for the protocol version

packages/rn-sdk/src/bridge/MessageRouter.ts:9 hardcodes a local const BRIDGE_PROTOCOL_VERSION = 1, duplicating packages/webview-bridge/src/types.ts:152. Reconcile:

  • Import BRIDGE_PROTOCOL_VERSION from @selfxyz/webview-bridge (re-exported at packages/webview-bridge/src/index.ts:37) and delete the local constant.
  • Confirm rn-sdk already depends on @selfxyz/webview-bridge (it does — package.json dependencies, workspace:^). No new dep.

The constant is the single source of truth for the number, not the enforcement. Each side of the bridge enforces independently against it: webview-bridge/src/schema.ts:105 validates host→WebView messages on the WebView side; MessageRouter.ts:59 validates WebView→host messages on the host side. Task 2 fixes the host side.

Task 2 — Fail closed on a missing version, and surface the mismatch to the host

In MessageRouter.ts:59-77 the guard is typeof request.version === 'number' && request.version !== BRIDGE_PROTOCOL_VERSION. This fails open when version is absent. Change it to treat a missing/non-numeric version as a mismatch (default-deny).

Precedent: webview-bridge/src/schema.ts:105 already fails closed — assertNumber(parsed, 'version') throws before the parsed.version !== BRIDGE_PROTOCOL_VERSION check, so a missing version is rejected there. MessageRouter's typeof === 'number' && is the inconsistent outlier; this task aligns it.

The router currently only replies to the WebView with the UNSUPPORTED_VERSION error code and returns — the host UI never learns. Add a notification channel:

  • Extend RouterConfig (MessageRouter.ts:29-32) with onVersionMismatch?: (info: { received: unknown; expected: number }) => void.
  • Fire it inside the mismatch branch (:59-77) before returning, in addition to the existing error response. The router stays policy-free — it reports received and lets the host decide the UX.
  • Keep sending the UNSUPPORTED_VERSION response (the WebView still gets a clean rejection).
  • Fix the now-stale error message at MessageRouter.ts:72: it interpolates ${request.version}, which renders as "version undefined not supported" once a missing version reaches this branch. Make it tolerate a non-numeric/absent value (e.g. received ${String(request.version)}) so the rejection log stays legible.

The version gate is request-scoped — it sits after if (request.type !== 'request') return; (MessageRouter.ts:55-57), so only inbound request messages are checked. That is correct: the host only ever receives requests from the WebView (it pushes events / sends responses the other way). Don't widen the gate to all message types.

In SelfVerification.tsx:

  • Add a terminal stage to the LoadStage union (:124): 'loading' | 'slow' | 'failed' | 'ready' | 'version_mismatch'.
  • Pass onVersionMismatch into the MessageRouter construction (:205-214). In the callback, branch on received: typeof received === 'number' → setLoadStage('version_mismatch') (terminal — definitive incompatibility); otherwise → setLoadStage('failed') (recoverable — a missing or malformed version is most likely transient). Fire the diagnostics reporter (Task 4) in both cases.
  • In the loading-timer effect (:293-306) and the render guard (:364-366), treat 'version_mismatch' as terminal: do not arm/keep timers, keep the overlay shown. 'failed' stays recoverable — retry re-arms timers, as today.
Decision (UX-first): fail closed on dispatch for any non-matching or absent version — the message is never processed (security). But the user only hits the terminal "Please update Self app" dead-end when the version is present-but-wrong (a retry is genuinely futile against the frozen bundle). A missing/non-numeric version routes to the recoverable error with retry — don't trap the user behind a dead button for what is most likely a transient frame. onVersionMismatch's received is the discriminator (a number → terminal; undefined/non-number → recoverable) and flows into the Sentry detail either way.

Task 3 — Fast-fail on hard WebView load errors

Today a missing/corrupt bundle only surfaces via the 10s timeout. Wire the WebView element (:350-363) to fail fast:

  • onError and onHttpError → setLoadStage('failed') and fire the diagnostics reporter with the platform error.
  • Android onRenderProcessGone → setLoadStage('failed') + reporter (renderer crash).
  • Guard each so a late event after ready does not regress the stage (mirror the stage === 'ready' ? stage : … pattern at :299-301).

Task 4 — Injected diagnostics reporter

Add an optional reporter prop to SelfVerificationProps, next to analytics?: AnalyticsSink (:99): 

onLoadDiagnostic?: (event: {
  kind: 'timeout' | 'load_error' | 'version_mismatch';
  source: 'bundle' | 'dev-server';
  detail?: Record<string, unknown>;
}) => void;
  • One taxonomy: diagnostic kind and the LoadStage/renderError literal both use version_mismatch (snake_case, matching load_error). No more protocol_mismatch vs version-mismatch drift.
  • Derive source from whether the __DEV__ + devServerUrl branch was taken (:322-327).
  • Fire it on: the 10s failed transition (:299-301), the Task 3 error handlers, and the Task 2 mismatch callback. Note a missing version fires kind: 'version_mismatch' with detail.received = undefined even though its stage is the recoverable failed — the diagnostic records the cause, the stage records the UX.
  • Do not import Sentry. The consumer (Task 6) maps kind → Sentry.captureException with tags runtime: rn-host and webview_source: <source>, per the spec invariants.

Task 5 — Render-prop slots + local-palette default, split recoverable vs terminal

Replace the raw-hex inline LoadingOverlay (:371-416):

  • Add renderLoading?: (stage: 'loading' | 'slow') => React.ReactNode and renderError?: (info: { kind: 'timeout' | 'load_error' | 'version_mismatch'; canRetry: boolean; onRetry: () => void }) => React.ReactNode to the props.
  • Map loadStage → render-prop: loading/slow → renderLoading; failed → renderError({ kind: 'timeout' | 'load_error', canRetry: true, onRetry }); version_mismatch → renderError({ kind: 'version_mismatch', canRetry: false, onRetry }).
  • Token source. rn-sdk has no design-token package and must not add Euclid (see Locked decisions), so there is no "shared" token module to import. Define a single local palette constant in rn-sdk — a module-level const COLORS = { bg: '#000', fg: '#fff', … } in a new packages/rn-sdk/src/theme.ts (or co-located at the top of SelfVerification.tsx if you prefer one file) — and reference it everywhere a color is needed. The goal is one source of truth, not scattered literals; this is the pragmatic reading of the "design tokens over hex" rule for a near-zero-dependency embeddable shell.
  • When the consumer passes nothing, fall back to a built-in default that reads from that local palette (no inline hex literals) and preserves the existing accessibilityRole="button" on retry. The default for version_mismatch shows "Please update Self app" and renders no retry button. Default copy is English-only — consumers localize via the render-prop.
  • Cover every hex site, not just the overlay. The raw-hex strings to replace are the overlay's (:386 backgroundColor, :391/393/396 spinner+text, :406 borderColor, :411 retry text) and the WebView's outer container at :349 (backgroundColor: '#000'). Route all of them through the local palette so no #000/#fff literal survives in SelfVerification.tsx.

Task 7 — Analytics funnel events (taxonomy decided during implementation)

The SDK already injects an analytics sink — analytics?: AnalyticsSink on SelfVerificationProps (:99), forwarded to createHandlers (:246) and available in the component body. This is a separate channel from the Sentry diagnostics in Task 4: diagnostics are error telemetry; analytics is the product funnel — how many users hit a load failure or the "update Self app" wall before verifying.

Fire funnel events through the existing analytics sink (not Sentry) on the failure / terminal transitions:

  • the 10s timeout → failed (:299-301);
  • the Task 3 hard load errors (onError / onHttpError / onRenderProcessGone);
  • the terminal version_mismatch;
  • consider the recovered case too — a load that failed then reached ready after retry.
Decision deferred (finalize while implementing — the funnel shape will be clearer then): the exact event names, properties, and which transitions deserve an event. Follow the app's existing analytics event-naming convention — do not invent a parallel scheme — and keep it funnel-shaped, not a duplicate of the Sentry diagnostic stream. Starting proposal: one webview_load_failed event with { kind, source } and one terminal webview_version_mismatch event; refine against the funnel as you wire it.

Constraints:

  • No new analytics dependency — reuse the injected AnalyticsSink.
  • Fire-and-forget — never block the load or error UI on an analytics call.
  • Keep diagnostics (Task 4, Sentry) and analytics (funnel) as distinct calls: same trigger points, different sinks, different payloads.
