Context

You are adding a host-minted correlation id that lets an engineer join every Sentry event from one WebView session — across the RN host and the WebView runtime. This is PR1 of WIA-14; PR2 (the footer) displays this id on error screens. Cross-runtime correlation is the whole point of the ANA-15 re-home, and it has no working key today.

Why a new id (verified in code). The original WIA-14/SPEC-OBSERVABILITY plan assumed attempt_id. That id is generated by the onboarding funnel (packages/mobile-sdk-alpha/src/analytics/onboardingFunnel.ts:38), which is driven exclusively by the RN app — webview-app calls none of its functions, no bridge message carries it, and getCurrentAttemptId() is always null in the WebView runtime. The only id the WebView has is verificationId, which is absent in self-app onboarding mode (the code already synthesizes verificationId ?? webview-${'{'}Date.now(){'}'} at packages/webview-app/src/utils/selfAppContext.ts:65). So neither existing id correlates across runtimes for every failure screen. PR1 introduces one that does.

Decisions

  1. The RN host mints correlationId once per SelfVerification load. A UUID (crypto.randomUUID() with the same fallback as packages/rn-sdk/src/bridge/MessageRouter.ts:11). It is the durable identity of one WebView session and is always present for RN-hosted WebViews, including self-app onboarding. Not a WebView-side fallback — the verificationId ?? webview-${'{'}Date.now(){'}'} shape is runtime-local, timestamp-derived, and can diverge from the RN host; it is not a correlation key.
  2. It propagates two ways, redundantly: appended to the WebView URL query string (buildRequestSearch) and returned from lifecycle.getConfig. The URL copy lets the WebView tag Sentry before the bridge handshake resolves; the config copy is the authoritative source. The WebView prefers the config value and falls back to the URL param.
  3. Both runtimes set a durable Sentry tag correlation_id as soon as the id is known — outside any analytics path. The RN analytics handler only forwards WebView event payloads (packages/rn-sdk/src/handlers/AnalyticsHandler.ts:32) and tagsFromAnalyticsEvent() only emits tags for onboarding-prefixed event names, so an event payload is not a reliable propagation path: a Sentry error thrown outside an analytics call would miss the tag. Set it via Sentry.setTag on the scope at session start on each side.
  4. verificationId stays a separate business id. It is tagged verification_id only when present. It is never aliased to correlation_id — aliasing reintroduces the onboarding-mode ambiguity this PR removes.
  5. No bridge protocol version bump. correlationId is an optional field on the existing getConfig response (and an optional URL param). Older hosts that omit it and standalone browser mode degrade gracefully (see Compatibility). Protocol stays BRIDGE_PROTOCOL_VERSION = 1 (packages/webview-bridge/src/types.ts:152).

Naming & casing

camelCase in code, snake_case at the Sentry/analytics boundary, mapped in exactly one place per runtime — the existing repo pattern (tagsFromAnalyticsEvent maps country_code → document_country at packages/mobile-sdk-alpha/src/observability/onboardingContext.ts:47). Do not standardize casing globally.

Implementation

  1. rn-sdk type + mint. Add the field to VerificationRequest. In the component body, const correlationId = useMemo(() => request.correlationId ?? makeUuid(), [request.correlationId]) where makeUuid matches MessageRouter's crypto.randomUUID()-with-fallback. Thread correlationId into buildRequestSearch(request, correlationId) and the LifecycleHandler config object built at SelfVerification.tsx:~407,432.
  2. rn-sdk getConfig. Add correlationId to LifecycleConfig and return it alongside mode/verificationRequest.
  3. RN Sentry helpers. In app/src/config/sentry.ts add the two allowlist keys and export setCorrelationTag (guards through the existing allowlist check at line 142) / clearCorrelationTag. The dev host (app/src/screens/dev/WebViewHostScreen.tsx:117) and any production consumer wire these through SelfVerification's mount/unmount, so callers do nothing.
  4. WebView config read. Add correlationId to HostConfigResponse and OperatingModeContextValue; in the success branch set correlationId: config?.correlationId ?? urlCorrelationId; in the catch (browser-host) branch set the URL value (or undefined). Parse the URL param in verificationRequest.ts.
  5. WebView Sentry helper + wiring. Add setCorrelationTag/clearCorrelationTag to webview-app/src/config/sentry.ts. In SelfClientProvider, an effect keyed on [correlationId, verificationId] calls setCorrelationTag when correlationId is set and returns a cleanup that clears it.

Tag lifecycle

  • Set: on each runtime as soon as the id is known — RN on SelfVerification mount, WebView when config/URL resolves.
  • Clear: RN on SelfVerification unmount and on dismiss/terminal setResult; WebView on provider unmount. A new load mints a new id and overwrites the tag. This prevents one failed session's correlation_id leaking into a later session's events.
  • verification_id tracks correlationId. setCorrelationTag(correlationId, verificationId?) clears verification_id when called without a verificationId, so a self-app onboarding session that follows an embed session does not inherit the prior session's verification_id. Both runtimes do this.
  • Invariant: correlation_id and verification_id reflect the current WebView session or are absent — never stale.

Compatibility

  • Old host, new WebView: getConfig omits correlationId and no URL param is present → the WebView has no correlation id; the footer (PR2) renders nothing. No error.
  • Standalone browser mode: no RN host. The WebView MAY synthesize a dev-only local id so local testing has a value, but it is not cross-runtime correlatable and must be documented as such (and gated to non-production). Default: render nothing rather than a misleading id.
  • New host, old WebView: extra config field + URL param ignored. RN still tags its own events. No regression to the existing Self Wallet app.

Tests

  • rn-sdk. buildRequestSearch includes correlationId when set; a provided request.correlationId is used verbatim; absent → a UUID is minted and stable across re-renders. LifecycleHandler.getConfig returns correlationId.
  • RN Sentry helper. setCorrelationTag sets correlation_id (and verification_id when provided; clears verification_id when absent); a non-allowlisted key is rejected; clearCorrelationTag removes both.
  • WebView config. OperatingModeProvider exposes correlationId from config; falls back to the URL param when config omits it; undefined when neither is present.
  • WebView Sentry helper. setCorrelationTag tags correlation_id via the mocked @sentry/react setTag; sanitizes the value; clears verification_id when absent; clears both on cleanup.

Out of scope

  • The footer UI (PR2 — WIA-14-footer).
  • Bridge protocol version changes or new domains/methods.
  • Aliasing or removing verificationId; touching attempt_id / the onboarding funnel.
  • Tag taxonomy changes owned by the analytics/ workstream (you add only correlation_id + verification_id, the keys this feature requires).
