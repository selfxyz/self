Context

You are adding flow-level integration tests to webview-app that lock in the WIA-12/13/14 observability work and the onboarding/failure routing, driven by an injected mock bridge. Today's webview-app tests (vitest + @testing-library/react, jsdom) render screens in isolation and mock useSelfClient per file. What is uncovered is the router-driven sequence across screens and the bridge round-trips that connect them. These tests close that gap deterministically, with no device and no real native side.

The injection point already exists: @selfxyz/webview-bridge/mock exports MockNativeBridge (a NativeTransport that routes domain/method calls to registered handlers). A WebViewBridge wired to a MockNativeBridge behaves like the real bridge to all of webview-app — the same contract the RN host speaks — while letting a test resolve or reject camera.scanMRZ, nfc.scanPassport, secureStorage.*, lifecycle.getConfig, etc. with fixed payloads.

This does not block merging feat/webview-in-app. It is an additive, test-only PR (plus one backwards-compatible provider prop). The umbrella branch ships without it; this lands on the branch (or on dev after) to guard the observability work against regression.

Decisions

  1. Inject a real WebViewBridge backed by MockNativeBridge — do not mock useSelfClient. The point of a flow test is to exercise the real adapter + createSelfClient wiring and the real bridge contract. Per-file useSelfClient mocks (as in embedFlowScreens.test.tsx) stay valid for narrow screen tests, but flow tests use the live provider tree so routing, adapters, and bridge serialization all run.
  2. Add a test seam to BridgeProvider. It currently constructs its own WebViewBridge internally with no injection point. Add an optional bridge?: WebViewBridge prop — when provided, use it; otherwise build the default (current behavior). This is the only production change and is backwards-compatible. Do not export BridgeContext for tests; the prop is the seam.
  3. One shared render helper. tests/utils/renderWithBridge.tsx mounts the full provider stack (BridgeProvider → OperatingModeProvider → VerificationRequestProvider → SelfClientProvider) inside a MemoryRouter at a given initialEntries, with a MockNativeBridge whose handlers the test supplies. Returns the bridge + RTL utilities. Every flow test builds on it; no per-file provider boilerplate.
  4. Drive flows through the router, assert on rendered screens. Start at the route under test, fire the user action (press “scan”), let the mock handler resolve, and assert the next screen renders. This is the behavior these tests exist to protect — not that a mock was called.
  5. Seed referenceId and operating mode deterministically. For WIA-14 footer and mode-routing assertions, seed via the same paths PR1 documented: the ?referenceId= URL param on the MemoryRouter entry, or a mock lifecycle.getConfig response carrying mode + referenceId. No new seam.

Implementation

  1. Seam. BridgeProvider gains bridge?: WebViewBridge; const bridge = useMemo(() => props.bridge ?? new WebViewBridge({...}), [props.bridge]). Existing callers pass nothing → unchanged.
  2. Helper. In renderWithBridge, construct new MockNativeBridge(), register the test's handlers (mock.on('camera','scanMRZ', () => mrzFixture) — match the real MockNativeBridge registration API), build a WebViewBridge over that transport, and pass it to BridgeProvider bridge={...}. Wrap in MemoryRouter initialEntries={[path]} and the remaining providers, mirroring App.tsx's tree order.
  3. Flow tests. Start at the capture entry route, fireEvent.click the scan CTA, await waitFor the success/error screen, assert by role/text. Use fixtures for MRZ + chip payloads; keep them in the test file or a small tests/fixtures/ module if shared.
  4. Footer + mask assertions. Reuse the seeding paths from WIA-14 and the PrivacyMask class contract from WIA-13. Do not duplicate the unit-level coverage those PRs already added (supportReference.test.tsx, PrivacyMask.test.tsx) — assert the integration: the footer/mask appears on the real screen reached through routing.

Deferred: Maestro device-flow expansion (scope only — do NOT implement now)

The on-device end-to-end is the Maestro flow at app/tests/e2e/webview-host-rn-sdk.android.flow.yaml, invoked by .github/workflows/mobile-e2e.yml. It currently launches the dev-menu WebView host and asserts the bundle loads. Expanding it is deferred until after WIA-11 (cutover) — until then the WebView path is dev-menu-gated and the real chip/camera reads need physical hardware the CI runners don't have. This section captures the target so the work is scoped, not lost.

Post-WIA-11 expansion targets (each a row to add to the Maestro flow, against a real or instrumented device):

  • Passport: dev-menu → WebView host → country picker → passport instructions → MRZ scan launches → NFC step → assert success or the euclid error screen on cancel.
  • EU-ID: same shape through the ID-card route.
  • Aadhaar: reach UploadErrorRoute via the placeholder reject (until a native handler ships).
  • Reference footer: on a forced failure, assert the Reference: line renders (text match).
  • Wire any new flow file into mobile-e2e.yml alongside the existing webview-host-rn-sdk job; respect the Namespace runner concurrency limits.
Real-device NFC/MRZ reads remain a manual hardware step regardless of Maestro — the emulator surfaces nfc_not_supported. Maestro can drive navigation and assert UI states; it cannot read a chip.

Out of scope

  • Playwright / Cypress / any real-browser harness. The browser-unique signals (Session Replay internals, real bridge transport) are either Sentry-owned or already covered by the on-device Maestro path. A headless browser would mock the bridge anyway — the vitest flow tests get that coverage without new CI infrastructure on a surface still churning toward cutover.
  • Implementing the Maestro expansion. Scoped above; deferred to post-WIA-11.
  • Any app/src or native change. webview-app tests only, plus the one BridgeProvider prop.
  • New bridge methods or domains. Tests register mock handlers for existing methods only.
  • Re-testing the legacy RN NFC path. Untouched by this workstream; no regression surface.
