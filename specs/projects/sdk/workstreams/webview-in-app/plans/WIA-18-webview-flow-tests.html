Context

You are adding flow-level integration tests to webview-app that lock in the WIA-12/13/14 observability work, WIA-16 mode routing, and the onboarding/failure routing, driven by an injected mock bridge. Today's webview-app tests (vitest + @testing-library/react, jsdom) render screens in isolation and mock useSelfClient per file. What is uncovered is the router-driven sequence across screens and the bridge round-trips that connect them. These tests close that gap deterministically, with no device and no real native side.

The injection point already exists: @selfxyz/webview-bridge/mock exports MockNativeBridge (a NativeTransport that routes domain/method calls to registered handlers). A WebViewBridge wired to a MockNativeBridge behaves like the real bridge to all of webview-app — the same contract the RN host speaks — while letting a test resolve or reject camera.scanMRZ, nfc.scanPassport, secureStorage.*, lifecycle.getConfig, etc. with fixed payloads.

The tests must mount the real App route table. Do not recreate selected Route entries inside the test helper; that would create a second routing contract and miss future route drift. Add a narrow router injection seam to App so tests can use MemoryRouter while production keeps BrowserRouter.

This does not block merging feat/webview-in-app. It is an additive, test-only PR (plus narrow backwards-compatible test seams). The umbrella branch ships without it; this lands on the branch (or on dev after) to guard the observability work against regression.

Decisions

  1. Inject a real WebViewBridge backed by MockNativeBridge — do not mock useSelfClient. The point of a flow test is to exercise the real adapter + createSelfClient wiring and the real bridge contract. Per-file useSelfClient mocks (as in embedFlowScreens.test.tsx) stay valid for narrow screen tests, but flow tests use the live provider tree so routing, adapters, and bridge serialization all run.
  2. Add a test seam to BridgeProvider. It currently constructs its own WebViewBridge internally with no injection point. Add an optional bridge?: WebViewBridge prop — when provided, use it; otherwise build the default (current behavior). Do not export BridgeContext for tests; the prop is the seam. Keep the default bridge memoized exactly once for normal callers, then select injectedBridge ?? defaultBridge; do not rebuild the default bridge when a test prop changes.
  3. Add a router seam to App. Today App owns BrowserRouter, which blocks MemoryRouter initialEntries. Extract the provider + Routes body into an internal component (for example AppRoutes) and let App accept an optional router?: React.ReactNode or equivalent wrapper prop. Production still renders BrowserRouter; tests render the same AppRoutes inside MemoryRouter. This is the only additional production seam allowed by WIA-18.
  4. One shared render helper. tests/utils/renderWithBridge.tsx mounts the full app (BridgeProvider bridge={...} → App using the test router seam) inside a MemoryRouter at a given initialEntries, with a MockNativeBridge whose handlers the test supplies. The helper must reuse the real provider stack and route table from App.tsx; no per-file route/provider boilerplate.
  5. Drive flows through the router, assert on rendered screens. Start at the route under test, fire the user action (press “scan”), let the mock handler resolve, and assert the next screen renders. This is the behavior these tests exist to protect — not that a mock was called.
  6. Seed referenceId and operating mode deterministically. For WIA-14 footer and mode-routing assertions, seed via the same paths PR1 documented: the ?referenceId= URL param on the MemoryRouter entry, or a mock lifecycle.getConfig response carrying mode + referenceId. No new seam.
  7. Register baseline bridge handlers in the helper. SelfClientProvider awaits lifecycle.getConfig and secureStorage.get/set/remove during normal app render/flows; document persistence in this app goes through createKeychainDocumentsAdapter, so it also uses secureStorage keys such as self_document_catalog and self_doc_*. The helper provides deterministic defaults for awaited requests and lets individual tests override flow-specific handlers. Fire-and-forget bridge calls (analytics.*, haptic.trigger, lifecycle.ready, lifecycle.dismiss) can be asserted through mock.messages if needed but do not need handlers just to keep the test running.

Implementation

  1. Bridge seam. BridgeProvider gains bridge?: WebViewBridge. Build defaultBridge with the current new WebViewBridge({...}) logic in a zero-dependency useMemo, then provide bridge ?? defaultBridge. Existing callers pass nothing → unchanged.
  2. Router seam. In App.tsx, extract the existing <OperatingModeProvider>...<Routes>...</Routes> subtree behind an exported internal component or a wrapper prop. Tests must render that real subtree inside <MemoryRouter initialEntries={...}>; they must not copy the ModeRoute list into test files.
  3. Mock bridge wiring. In renderWithBridge, construct new MockNativeBridge(), register default handlers with the real API (mock.handle(...) / mock.handleWith(...) / mock.handleWithError(...)), build new WebViewBridge({ transport: mock }), then call mock.connect(bridge) before rendering BridgeProvider bridge={bridge}.
  4. Default handlers. Provide deterministic helper defaults for awaited requests: lifecycle.getConfig (default { mode: 'self-app' } plus caller overrides), lifecycle.setResult if a tested close/result path awaits it, and secureStorage.get/secureStorage.set/secureStorage.remove. Model secure storage with a per-test Map<string, string>; this covers document catalog and document body persistence because createKeychainDocumentsAdapter stores them under self_document_catalog and self_doc_*. Let tests override any default by registering their handler after defaults.
  5. Flow tests. Start at the real capture route, click through where that is the behavior under test, and await waitFor the success/error screen. For flows whose previous screen is already covered (for example NFC failure), it is acceptable to start at the NFC route with realistic location.state so the assertion stays focused on the bridge failure and route outcome.
  6. Footer + mask assertions. Reuse the seeding paths from WIA-14 and the PrivacyMask class contract from WIA-13. Do not duplicate the unit-level coverage those PRs already added (supportReference.test.tsx, PrivacyMask.test.tsx) — assert the integration: the footer/mask appears on the real screen reached through routing.

Deferred: Maestro device-flow expansion (scope only — do NOT implement now)

The on-device WebView-host Maestro flow exists at app/tests/e2e/webview-host-rn-sdk.android.flow.yaml, but .github/workflows/mobile-e2e.yml currently runs only the baseline launch.android.flow.yaml and launch.ios.flow.yaml flows. The WebView-host flow is not wired into CI today. Wiring or expanding it is deferred until after WIA-11 (cutover) — until then the WebView path is dev-menu-gated, mobile-e2e.yml does not trigger for packages/webview-app/**-only changes, and the real chip/camera reads need physical hardware the CI runners don't have. This section captures the target so the work is scoped, not lost.

Post-WIA-11 expansion targets (each a row to add to the Maestro flow, against a real or instrumented device):

  • Passport: dev-menu → WebView host → country picker → passport instructions → MRZ scan launches → NFC step → assert success or the euclid error screen on cancel.
  • EU-ID: same shape through the ID-card route.
  • Aadhaar: reach UploadErrorRoute via the placeholder reject (until a native handler ships).
  • Reference footer: on a forced failure, assert the Reference: line renders (text match).
  • Wire webview-host-rn-sdk.android.flow.yaml or any successor flow into mobile-e2e.yml as a post-WIA-11 follow-up; respect the Namespace runner concurrency limits.
Real-device NFC/MRZ reads remain a manual hardware step regardless of Maestro — the emulator surfaces nfc_not_supported. Maestro can drive navigation and assert UI states; it cannot read a chip.

Out of scope

  • Playwright / Cypress / any real-browser harness. The browser-unique signals (Session Replay internals, real bridge transport) are either Sentry-owned or already covered by the on-device Maestro path. A headless browser would mock the bridge anyway — the vitest flow tests get that coverage without new CI infrastructure on a surface still churning toward cutover.
  • Implementing the Maestro expansion. Scoped above; deferred to post-WIA-11.
  • Any app/src or native change. webview-app tests only, plus the BridgeProvider and App seams described above.
  • New bridge methods or domains. Tests register mock handlers for existing methods only.
  • Re-testing the legacy RN NFC path. Untouched by this workstream; no regression surface.
