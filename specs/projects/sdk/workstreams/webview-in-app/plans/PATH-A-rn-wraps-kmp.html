Why this PR exists

The webview-in-app workstream's Native Adapters spec (Decision 1) commits to building a new SelfCrypto native module inside packages/rn-sdk/. But packages/kmp-sdk/ already has Kotlin-side handlers for secureStorage, crypto, and lifecycle, delegated through a Provider Registry pattern. Building them twice — once in kmp-sdk for the native-Kotlin consumer, once in rn-sdk for Self Wallet — is duplication that grows linearly with every future bridge change.

A confirmed external native-Kotlin consumer exists, so kmp-sdk cannot be retired. The only question is whether rn-sdk reuses kmp-sdk's router and handlers or runs parallel.

Full research findings (two-repo split, KMP iOS provider model, publishing posture, router envelope drift) are in SPIKE-rn-wraps-kmp.md. This page is the one-page summary used to scope this PR.

Decision — Path A, prototype-first

You are proving the binding model on one domain, one platform. If the prototype works, a follow-up workstream replaces the remaining TS handlers and retires the duplicated router. If the prototype hits an abort condition, the work is discarded and the current webview-in-app SPEC stands.

The prototype lives behind a feature flag — existing TS handlers and the existing SelfVerification behavior are untouched. The PR is mergeable to feat/webview-in-app without changing default behavior for Self Wallet or any existing consumer.

PR scope

In scope

  • Local-Maven publishing path for packages/kmp-sdk/ validated via ./gradlew publishToMavenLocal.
  • New Kotlin module SelfBridgeModule inside packages/rn-sdk/android/ that consumes the KMP AAR, owns one MessageRouter instance, and registers EncryptedSharedPreferencesProvider + SecureStorageBridgeHandler at init.
  • Bridge entry point exposed to JS: NativeModules.SelfBridge.routeMessage(rawJson); responses flow back via DeviceEventEmitter on channel SelfBridge:response.
  • A feature flag (useKmpBridge prop on <SelfVerification>, default false) that routes only secureStorage.* calls through the new path and leaves every other domain on the existing TS router.
  • Smoke validation in packages/rn-sdk-test-app/: round-trip secureStorage.set('k','v') → secureStorage.get('k') → secureStorage.remove('k') via a stub WebView page.

Not in scope (explicit non-goals)

  • iOS. Defer until Android proves the binding model — KMP iOS still has cinterop disabled and stub handlers, and adds a layer of unknown the prototype does not need.
  • Replacing or deleting existing TS handlers. They keep working as the default path.
  • Self Wallet (app/) integration. The prototype is exercised from rn-sdk-test-app.
  • Remote publishing of KMP artifacts. SD-06 (SELF-2534) is already specced and owned by someone else; this PR uses mavenLocal().
  • Convergence of the selfxyz/self ↔ selfxyz/self-webview-sdk kmp-sdk forks. This PR consumes this repo's packages/kmp-sdk/ as-is.
  • Bridge protocol envelope cleanup (the small KMP vs TS drift documented in the research notes).

Architecture

Before this PR (default path, unchanged)

WebView → onMessage → TS MessageRouter → TS handler (e.g. KeychainHandler.ts)
                                   → react-native-keychain → Keystore

After this PR (only when useKmpBridge + domain = secureStorage)

WebView → onMessage → SelfBridgeModule (Kotlin)
                       → kmp-sdk MessageRouter
                       → SecureStorageBridgeHandler
                       → EncryptedSharedPreferencesProvider
                       → AndroidX EncryptedSharedPreferences

For every other domain (nfc, camera, biometrics, crypto, haptic, analytics, lifecycle, documents, navigation), the existing TS path runs even when useKmpBridge is on. The prototype is additive, not a swap.

Out of scope (do not do)

  • Modify any existing TS handler. Touching KeychainHandler.ts defeats the "additive prototype" framing.
  • Change the bridge protocol shape. The router envelope drift (DOMAIN_NOT_FOUND vs HANDLER_NOT_FOUND, missing type/version/timestamp in KMP responses) is real and must be patched eventually, but not in this PR. The TS shim normalizes the response shape so the WebView never sees the drift.
  • Touch packages/kmp-sdk/shared/src/iosMain/ or packages/self-sdk-swift/. iOS is deferred.
  • Set up CI for the KMP-publishing → rn-sdk-consuming build. Local-only validation is enough for the prototype.
  • Edit SPEC-NATIVE-ADAPTERS.md's Decision 1. If the prototype succeeds, a follow-up PR amends that spec; if it fails, the spec stands.
  • Try to make this prototype work with a hosted Maven (GitHub Packages). SD-06 owns that infrastructure work.

Abort conditions

Stop the prototype and write up findings without merging if any are true:

  1. KMP AAR cannot be consumed by packages/rn-sdk/android/build.gradle without making the host app add bespoke repositories (mavenLocal in particular doesn't propagate transitively the way mavenCentral does; if the only path is "Self Wallet's settings.gradle must reference mavenLocal," that's an unacceptable consumer-side leak for a prototype).
  2. Kotlin version conflicts between rn-sdk/android's 1.9.24 and kmp-sdk's Kotlin Multiplatform plugin can't be resolved without forcing the host app onto a specific Kotlin version.
  3. The native glue total (the two new Kotlin files) exceeds ~250 LOC.
  4. Round-tripping secureStorage.set takes longer than 50ms on a release build on a recent emulator.
  5. The RN module instance lifecycle and the WebView lifecycle interact in a way that requires non-trivial cleanup logic (e.g. router coroutine scope leaks on RN reload).
  6. Prototype runs longer than 5 working days from the start of implementation.

Smoke acceptance:

  1. Toggle useKmpBridge on in the test screen.
  2. Stub WebView posts { domain: "secureStorage", method: "set", params: { key: "self.test", value: "hello" } }; response arrives with success: true.
  3. Stub WebView posts { domain: "secureStorage", method: "get", params: { key: "self.test" } }; response arrives with data: { value: "hello" }.
  4. Stub WebView posts { domain: "secureStorage", method: "remove", params: { key: "self.test" } }; subsequent get returns data: { value: null }.
  5. Toggle useKmpBridge off; the same round-trip continues to work through the existing TS handler.

Open risks (not abort-worthy, but worth tracking)

  • Two-repo split. selfxyz/self-webview-sdk holds a forked kmp-sdk where MOD-01/02/04 are landing. This PR uses this repo's packages/kmp-sdk/. If self-webview-sdk becomes canonical, this PR will need to re-target the artifact source before any follow-up. Convergence is a separate decision and is called out in the research notes.
  • Bridge protocol envelope drift. KMP responses are missing type, version, and timestamp fields that the TS protocol includes. The TS shim in this PR normalizes responses before the WebView sees them. Converging the two envelopes is a follow-up that should happen before any other domain migrates.
  • Path B is not closed by this PR. If the prototype passes, the next decision is "do we replace the remaining TS handlers and retire the duplicate router?" That's a workstream-level call, not a single PR.
