What this page is

This is the technical-decisions companion to the WIA-17 plan. The plan lists what ships per domain; this page argues the shape of the SDK once it does, with diagrams and a recommended answer for every open architectural question.

The frame. Today the same bridge protocol is implemented in three places: KMP shared, the RN-side TS handlers, and the native-shells-lite Kotlin/Swift packages. Every protocol change has to land three times. Path A retires one of them (RN). The CTO call captured here is to retire the other one too (native-shells-lite) once Path A is stable, leaving kmp-sdk as the single bridge implementation for every shell.

red = duplicate / drift risk  ·  green = single source of truth  ·  blue = thin shell / glue

Today — three parallel bridge implementations

Every consumer (Self Wallet RN, the external native-Kotlin partner, the OSS native-shell-ios sample) speaks the same JSON bridge protocol to the same WebView. But each one ships its own MessageRouter + handlers. Drift between them shows up as bugs the WebView can't tell apart (e.g. KMP returns DOMAIN_NOT_FOUND where TS returns HANDLER_NOT_FOUND).

Every bridge protocol change must be made three times. Every error-vocabulary tweak, every envelope-shape adjustment, every new method. The "WebView can't tell which shell" invariant in SPEC §Invariants is enforced by code review, not by construction.

Target — one bridge implementation, three thin shells

Path A collapses RN onto KMP. The follow-on (OQ-4) collapses native-shells-lite onto KMP too. End state: one MessageRouter, one set of handlers, one provider registry, with platform-specific provider impls injected at boot per host.

What this buys. Bridge protocol change = one PR in kmp-sdk. Error vocabulary = one file. The invariant becomes structural: the WebView can't tell which shell it's in because they all share the same router class. Drift becomes a compile error, not a code review concern.

A — vendor provider files in packages/rn-sdk/ios/
Self-contained: @selfxyz/rn-sdk npm tarball carries the Swift code. Duplicates what self-sdk-swift already has; every provider change has to land twice.
B — import from self-sdk-swift as a peer SPM dep Recommended
One source of truth for Swift providers. Mirrors the Android side (Android impls live in kmp-sdk/androidMain, not duplicated in rn-sdk/android/). Costs one line in selfxyz-rn-sdk.podspec.
Why: matches the Android pattern, eliminates a 2x maintenance cost forever. The cross-package coupling is small (one podspec dep) and explicit.

A — publish private fork as a Maven artifact (via SD-06)
Cleanest for keeping selfxyz/self OSS-slim. Couples rollout of #5–#7 to SD-06 shipping. Adds a release-coordination process between the two repos forever.
B — merge MOD modules back into selfxyz/self, gated by Gradle flag Recommended
MOD modules live in this repo's packages/kmp-sdk/shared/src/androidMain/; build flag self.sdk.optional.nfc=true opts them in. Default OSS distribution stays slim (flag off); Self Wallet's app/ turns the flags on. self-webview-sdk retires.
Why: eliminates the two-repo coordination cost permanently — every protocol change is one PR, every contributor sees the same code, no "is X in the right repo" friction. Public OSS surface stays slim via the Gradle flag, not via a repo split. Costs Seshanth one merge to unify; saves us every-PR-after-that. This is the kind of debt we should pay off now rather than amortize forever.
C — mirror script (sync the two repos)
Permanent dual maintenance. Drift inevitable. Not recommended under any framing.

OQ-4 Future workstream (not WIA-17)

Confirmed by reading the code: packages/native-shell-android/ and packages/native-shell-ios/ each ship their own MessageRouter + BridgeHandler classes (Kotlin and Swift), not consuming kmp-sdk. That's the third parallel implementation Path A doesn't touch.

OQ-5 After ≥3 domains migrated

How do we resolve the bridge envelope drift?

Observed drift between TS and KMP routers:

  • Missing-handler error: KMP DOMAIN_NOT_FOUND vs TS HANDLER_NOT_FOUND
  • KMP responses lack type / version / timestamp fields
  • KMP enforces isTrustedSource; TS has no equivalent
  • Malformed-message handling: KMP silent drop vs TS console.error
Make KMP's shape canonical · patch TS once Recommended
KMP is the source of truth for the WebView protocol per the umbrella spec. Patch packages/webview-bridge/ and the WebView-side adapters to match KMP's shape; everyone converges in one PR.
Why: directionally correct — Path A is putting KMP at the center anyway. Doing it once (after ≥3 domains have proven KMP's behavior under load) is cheaper than per-domain patches.
Keep KmpBridgeTransport.ts as a permanent shim that normalizes responses
Avoids touching WebView code. Hides drift behind a translation layer that has to be maintained alongside both routers — exactly the kind of "two-implementations-with-a-bridge" debt we're retiring elsewhere.
OQ-6 Final cleanup PR

What happens to the useKmpBridge flag once all domains migrate?

useKmpBridge is a per-domain routing flag in SelfVerification.tsx. It exists so each domain PR can ship additively (TS handler still runs by default; KMP path opt-in). After domain #8 lands and its TS handler is deleted, the flag has nothing to gate.

Delete the flag in the final cleanup PR Recommended
One small PR: removes the prop, removes the conditional branches in SelfVerification.tsx, removes the prop from any test app. Routing is unconditional through SelfBridgeModule.
Why: dead flags rot. Delete in the same change that makes them obsolete.
Keep the flag as a "debug TS fallback" for emergencies
Tempting but wrong: by the time all 8 TS handlers are deleted, there's no fallback to fall back to. Keeping the flag means keeping the TS code dead-but-undead "just in case."
OQ-7 Affects #8

Where does DocumentsBridgeHandler for Android come from?

Confirmed by file listing: this repo's kmp-sdk has a DocumentsBridgeHandler.kt in iosMain/ but not in androidMain/ or commonMain/. Either we add it here, or it arrives via OQ-2 (the MOD path).

Move to commonMain/ with a DocumentsProvider interface in the WIA-17 #8 PR Recommended
Matches the pattern from #1915 (which moved SecureStorageBridgeHandler and CryptoBridgeHandler to commonMain). Handler is platform-agnostic business logic; the provider interface gets Android and iOS impls.
Why: consistent with the architecture #1915 already established for the other handlers. The iOS version is small enough that promoting it to commonMain is roughly a file-move + interface extraction.
Wait for OQ-2's MOD path to deliver it
Couples #8 to OQ-2 unnecessarily. Documents is a wholly-public domain — there's no reason it should travel with the optional MOD modules.
OQ-8 Doesn't affect WIA-17 — captured to defer explicitly

Should KMP iOS cinterop be re-enabled?

packages/kmp-sdk/shared/build.gradle.kts:34-63 has cinterop disabled. That's why iOS handlers are NotImplementedError stubs that delegate to IosProviderRegistry. Re-enabling cinterop would let KMP iOS handlers call Keychain Services / Security framework directly — no Swift provider needed for stock impls.

Keep cinterop disabled · Swift providers via registry Recommended
Matches the Android pattern (KMP delegates to providers; some are KMP-internal, some are consumer-supplied). The Swift provider model gives RN/native-shell consumers a place to inject their own impls. Cinterop adds K/N toolchain risk and gives no architectural win we don't already have.
Why: the registry model is the right separation of concerns; cinterop would mix policy (in K/N) with mechanism (Swift APIs). Keep them on opposite sides of a clean interface.
Re-enable cinterop for stock iOS impls
Would let KMP own iOS Keychain / crypto directly. K/N cinterop is finicky; we'd own its maintenance. Doesn't compose well with the consumer-supplied provider model we keep for things like react-native-biometrics.

Settled — not asking

The following are not open questions. The plan treats them as decided.

  • Path A vs Path B · Path A confirmed by PR #2108's smoke pass and the resulting merge.
  • Per-domain PRs vs one big sweep · per-domain. Smaller revert windows; one of the durable preferences captured in CLAUDE.md.
  • TS handler retirement timing · same PR as each domain's migration, not a sweep at the end. Matches the "delete legacy in-PR" preference.
  • SD-06 for #1–#4 · not blocking; mavenLocal() sufficient for the rollout.
  • Hosted URL vs embedded bundle for Self Wallet v1 · embedded bundle, per SPEC-HOSTED-LOADING. Hosted is a post-v1 evolution.
  • Bridge protocol version · stays at 1 throughout this rollout. Envelope shape changes (OQ-5) are non-version-breaking.
