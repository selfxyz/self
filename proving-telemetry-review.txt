No. There is instrumentation in the proving flow, but it is not strong enough for InvalidRoot / stale-QR diagnosis.

Findings

1. InvalidRoot should emit analytics, but not in a way that is easy to find.
In the Socket.IO failure path, the machine logs a generic Sentry message "TEE processing failed" with error_code and reason in extras, then tracks SOCKETIO_PROOF_FAILURE with the raw payload (packages/mobile-sdk-alpha/src/proving/provingMachine.ts:830). Later the screen also tracks PROOF_FAILED with errorCode and reason (app/src/screens/verification/ProofRequestStatusScreen.tsx:282). So the signal exists, but it is fragmented.

2. Sentry will not index reason=InvalidRoot as a tag.
The Sentry tag allowlist includes error_code but not reason (app/src/config/sentry.ts:28). For stale QRs, the useful discriminator is usually the reason, not the error_code. That means the event may exist in Sentry as a generic message, but searching or alerting on InvalidRoot is effectively broken.

3. The analytics schema is inconsistent across proving failure call sites.
Different paths send:
- error_code / reason on SOCKETIO_PROOF_FAILURE (packages/mobile-sdk-alpha/src/proving/provingMachine.ts:840)
- errorCode / reason / state on screen-level PROOF_FAILED (app/src/screens/verification/ProofRequestStatusScreen.tsx:282)
- error on some lower-level PROOF_FAILED calls (packages/mobile-sdk-alpha/src/proving/provingMachine.ts:687)
This makes dashboards and queries brittle. A stale QR can miss whatever property name the dashboard expects.

4. “Mixpanel” may be the wrong place to look for proving analytics.
App trackEvent() goes through the Segment client, not the direct native Mixpanel path (app/src/services/analytics.ts:319). The direct Mixpanel code here is NFC-specific. So if you were checking raw Mixpanel-native instrumentation instead of the Segment-fed event stream, proving failures would look missing by design.

What worries me most

The stale-QR path is probably being recorded as a generic Sentry message and a couple of differently-shaped analytics events, but there is no canonical, searchable “proof terminal failure” record with normalized fields like:
- failure_kind
- state
- error_code
- reason
- terminal_source

That is exactly how you end up with “we know users hit it, but telemetry says nothing.”

What I’d change

1. Add reason to the Sentry tag allowlist, or add a normalized failure_reason tag derived from it.
2. Emit one canonical terminal event for every failure path, with one schema everywhere:
   error_code, reason, state, failure_kind, circuitType, sessionId, appName.
3. Add an explicit Sentry capture on terminal disclose failure, not just generic logProofEvent('error', 'TEE processing failed', ...).
4. Standardize analytics field names now. Pick one of error_code or errorCode and use it everywhere.
